# Untitled UI 集成策略

在现有项目选择集成模式、规划资源组合或基础 UI 接管边界时读取。目标是避免长期维护两套基础组件和样式体系，同时不把局部任务扩大为全仓重构。

## 直接集成

项目已使用 Untitled UI，或兼容矩阵全部满足时，原地使用 CLI。先把接管边界明确到一个可独立构建的应用或前端 package；单个页面接入不授权清理其他应用。

- Untitled UI components 作为该边界内的基础 UI component 层。
- Untitled UI foundations、Tailwind theme 与项目语义 token 作为视觉设计和运行时样式权威。
- 业务组件组合已有 primitives，不重新实现 Button、Input、Modal、Dropdown 等基础能力。
- 在任务范围内替换重复 primitives 和平行样式，不主动进行仓库级清理。
- 不使用任意 Tailwind values、硬编码颜色或页面级样式建立契约之外的视觉语言。
- 图表、地图、富文本、数据网格、Canvas/WebGL、打印样式、复杂 keyframes 和浏览器修复可按领域约束保留，但限制影响范围。

## 有限修复后集成

Next.js 或 React + Vite 项目只缺少少量前提，且可在不改变主要架构的情况下补齐时采用。允许的修复包括：

- 补充受支持的 Tailwind 插件、入口和必要依赖。
- 补充 TypeScript 路径别名、样式入口或 `components.json`。
- 在既有主版本内对齐组件目录、版本声明和语义 token。

若修复需要更换框架、重写路由、改变认证/接口/部署边界、升级组件库主版本或长期运行两套基础 UI，则不属于本模式。

完成当前功能后，列出剩余自定义 primitives、全局 CSS、CSS Modules、CSS-in-JS、重复 token 和旧组件依赖。完整迁移可以作为非阻塞建议，但范围和时机由用户决定。

## 仅参考

任一关键条件不满足时保留原技术栈：

- 不在目标项目运行 `untitled-cli init`、`add` 或 `example`。
- 可以只读搜索 template、example、组件和图标，参考信息层级、交互、状态与视觉策略。
- 使用当前框架和组件系统重新实现，不复制依赖 React/Untitled UI 的源码。
- 需要查看完整 example 时，仅在隔离的临时受支持项目安装；不要共享目标项目的 lockfile、依赖、配置、CSS 或运行时状态。
- 不创建 Agent 专用状态文件持久化本次判断。

不兼容本身不是询问重构的理由。只有用户明确要求迁移/统一基础层，现有技术栈无法合理安全地实现明确目标，或任务本身就是架构与基础设计系统重建时，才确认重构范围。确认应一次说明阻塞、局部适配为何不足、建议边界、可复用资产、风险、验证、回退方式和仅参考替代方案。

## 资源选择与组合

搜索先于安装。页面或流程优先检查接近目标的 example/template，再补充区块、基础组件和图标；单个基础组件任务不必搜索无关页面资源。实现前列出任务范围内全部用户可见或可交互的 UI 能力，并为每一项记录已安装资源检查结果；没有可复用项时，必须继续执行 Untitled UI CLI 搜索。记录候选的准确标识、类型、版本、权限、依赖、写入路径和状态覆盖，按用户目标及已提取的 Untitled UI + Tailwind 设计契约裁决后才安装。

组件复用遵循以下层级：

1. 复用项目已经安装的 Untitled UI 组件及其 variant。
2. 使用 CLI 搜索并安装 Untitled UI 已提供但项目尚未安装的组件。
3. 用 Untitled UI primitives、语义 token、props、`className`、wrapper 和组合构建业务组件。
4. 前述能力均无法覆盖明确需求时，记录具体缺口并提出隔离的最小自定义扩展。

在设计和实现前建立完整的界面能力清单，不按控件种类抽样，将每一项逐一匹配到现有或可安装的 Untitled UI 资源。浏览器具备基础行为、项目里已有原生实现或交付时间有限，都不代表资源检索已经完成；同时核对主题适配、状态覆盖、键盘交互和响应式表现。

当 Untitled UI 提供相应能力或可组合路径时，产品界面必须由其组件承担交互与呈现，以维持设计语言、状态模型和跨平台体验的一致性。不得把原生元素、第三方 UI 或自建基础组件当作默认替代；它们只有在完成已安装资源检查和 CLI 搜索、记录确切能力缺口，并取得相应扩展授权或用户明确要求平台原生体验后才可采用。原生元素可以作为组件内部的语义实现细节，但不能绕过对外的 Untitled UI 组件 API 和呈现。

实现完成后反向审计源码中的直接原生交互元素、第三方 UI 引用、手写弹层与交互状态、重复 primitives。每个命中项都必须能对应到已记录的库内部实现、明确平台要求或经批准的能力缺口；否则视为组件选型未完成并改用 Untitled UI。

不得直接修改已经安装的 Untitled UI component 或共享 primitive 源码。任何自定义能力都必须先记录已检索的 Untitled UI 资源、现有组合路径的限制和具体缺口，并取得扩展授权；自定义实现不能仅由局部视觉偏好或交付便利驱动。

若明确需求必须改变组件内部实现，且 props、variant、wrapper 和组合都会破坏所需语义或行为，则把所需实现复制到独立的自定义组件目录后再修改。自定义副本必须使用不同的组件名称、文件路径和导出入口，不替换原组件，也不改变现有调用方；同时记录复制来源、Untitled UI 版本、偏离原因和验证范围。选择目录时遵循项目既有约定；没有约定时建立清晰的 custom 边界，并确保后续 CLI 安装或升级不会覆盖该副本。

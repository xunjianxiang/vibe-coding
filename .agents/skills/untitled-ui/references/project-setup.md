# Untitled UI 项目创建

创建新项目、选择 CLI 支持的目标框架，或确认前后端边界时读取。框架选择服务于用户的产品、渲染与部署需求，不是为了使用 Untitled UI 而迁移技术栈。

## 选择目标框架

先判断服务端能力是否已经有独立归属。对于绿地项目，使用以下默认值，除非用户已经指定框架或产品约束要求其他选择：

| 项目事实 | 默认选择 |
| --- | --- |
| 前后端都使用 JavaScript/TypeScript，且没有独立服务或独立部署的明确需求 | Next.js 全栈应用 |
| Go、Java、Rust、Python 等后端已经或将独立提供 API | React + Vite 前端 |
| 已有独立 Node.js API，或组织/部署边界已经明确要求前后端分离 | React + Vite 前端，保留独立 API |

不要因为需求同时包含“前端”和“后端”，就自动创建 Express + React/Vite 两个应用。当前后端都可用 JavaScript/TypeScript 实现时，Next.js 的 Route Handlers、Server Actions、Server Components、中间件和服务端运行时已经能够承载所需服务端职责，且没有下述分离依据，则使用一个 Next.js 应用。不要再添加 Express、重复的 API 层、跨源配置或第二套部署单元。

优先选择或保留 Next.js：

- 需要 SEO、SSR、SSG、按路由生成元数据或公开首屏服务端输出。
- 需要 Server Components、Server Actions、中间件、BFF 或同仓库服务端能力。
- 产品是公开营销站、内容站、电商或需要同源认证代理。
- 绿地项目的前后端都使用 JavaScript/TypeScript，且同一团队、仓库和部署边界即可满足需求。

优先选择或保留 React + Vite：

- 产品是登录后的后台、管理台、内部工具或纯客户端 SPA。
- Go、Java、Rust、Python 或现有 Node.js 后端已经独立提供 API，不需要 SSR、SSG 或 Next.js 服务端能力。
- 更重视简单客户端架构、快速启动和静态部署。

只有存在具体边界时，才为绿地 JavaScript/TypeScript 全栈项目选择 Express + React/Vite 等分离架构，例如：

- API 需要独立扩缩容、独立发布、被多个客户端复用，或由不同团队负责。
- 服务端需要 Next.js 目标运行时不适合承载的长任务、常驻连接、协议、进程模型或基础设施。
- 安全、合规、网络或故障隔离要求独立服务边界。
- 用户明确指定分离架构。

“以后可能扩展”、个人习惯或前后端目录看起来更整齐，不构成新增 Express 服务的充分依据。后台或内部工具的 SPA 属性只说明它不需要 SSR；当服务端同样是待创建的 JavaScript/TypeScript 代码且没有独立边界时，仍优先使用 Next.js 收拢全栈职责，而不是机械选择 Vite + Express。

框架选择优先遵循用户明确要求和可验证的渲染、运行时、认证及部署需求，后端语言只是默认判断的一项证据。例如独立 Go API 不妨碍在确有 SEO/SSR 需求时使用 Next.js 作为 Web 层。信息充分时直接采用上述默认值；只有未决事项会实质改变服务边界或部署拓扑时才向用户确认，然后运行对应的 `init` 命令。

## 确认品牌色

创建新项目或首次配置现有项目时，先按 [brand-color.md](brand-color.md) 处理品牌色：

- 用户提示词没有提到颜色：不传 `-c/--color`，使用内嵌的默认品牌色 `#0BA5EC`。
- 用户提到明确颜色词：映射为 CLI 支持的色族名并传 `-c`，例如 `untitled-cli init my-app --nextjs -c blue`。
- 用户提到颜色但无法对应：不传 `-c`，使用默认品牌色，并在交付说明中写明使用了默认色。

不要为避免歧义再向用户追问颜色，也不要使用 `--colors-list` 交互流程；提示词已经给出或未给出颜色时都应直接继续。

## 确认工程边界

创建前明确：

- 实际前端根目录，以及单仓库、monorepo 或独立仓库布局。
- 包管理器和唯一 lockfile。
- 后端是 API、服务端模板、BFF 还是同仓库全栈应用。
- 若计划同时新建 JavaScript/TypeScript 服务端，记录为什么 Next.js 内置服务端能力不足；没有具体理由时不拆出 Express。
- Session/Cookie、Token、SSO 或第三方回调的认证边界，以及 CSRF、CORS 和 Cookie domain。
- 前后端独立部署、同域代理或同一运行时发布方式。
- TypeScript、路径别名、环境变量、路由和测试约定。

后端模板项目的窄维护默认保留原技术栈。只有用户明确批准独立 Web 前端或整体迁移时，才创建新的 Next.js/Vite 项目。不要机械引入未被需求使用的状态库、表单库、BFF 或测试框架；先复用 CLI 模板和组织已有标准。

## 迁移边界

现有项目只有在用户明确要求迁移或统一基础层、当前技术栈无法合理安全地实现明确目标，或任务本身就是架构重建时，才讨论目标框架。一次说明迁移范围、可复用资产、路由/认证/数据调整、测试、风险和回退方式；获得同意前不创建替代工程或修改框架级配置。

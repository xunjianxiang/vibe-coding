# Web UI Design & Development

这是 Web UI Skill 编排层，不是设计系统或实现 Skill。它说明谁参与、各自负责什么、按什么顺序交接，以及特殊集成事项如何处理；领域判断和执行细节始终归对应 Skill。

## 参与者

| Skill | 参与条件 | 负责内容 | 主要输出 | 特殊事项 |
| --- | --- | --- | --- | --- |
| `untitled-ui` | 项目采用、评估或接入 Untitled UI | 项目接管、设计系统基线、页面资源推荐、归口实施和技术验收 | 接管模式、设计系统契约、资源建议、实现与验证结果 | 读取 [references/untitled-ui.md](references/untitled-ui.md) |
| `impeccable` | 任务需要产品体验设计、界面审查或打磨 | 使用 `untitled-ui` 提供的资源完成产品流程、信息架构、内容层级、布局组合、响应式策略和体验设计 | 契约内的页面组合方案、审查结论和修复建议 | 读取 [references/impeccable.md](references/impeccable.md) |
| `animate` | 用户提出动效相关的请求 | 动效方案与实现，含交付前自检 | 动效方案、实现与自检结论 | 读取 [references/animate.md](references/animate.md) |
| 本 Skill | 参与者缺失或需要安装；或两个以上参与者需要协作 | 参与者选择、阶段顺序、交接、冲突归属和完成条件 | 聚合交付 | 不代替任何参与者执行领域工作 |

用户 brief、产品文档、必须保留的行为和授权边界是所有参与者的共同输入。

## 启动检查

1. 根据任务范围选择最小参与者集合；不因 Skill 可用就自动调用。
2. 确认当前 Agent 能发现准确名称的 Skill，并完整读取其 `SKILL.md`。CLI、npm package 或同名目录不能替代可加载的 Skill。
3. 仅对实际参与者读取其特殊事项参考，完成必要的项目级检测。
4. 参与者缺失时，先区分“当前 Agent 无法发现”与“目标项目尚未安装”。特殊事项给出恢复方式时按该参考执行：写入影响只限于自身 Skill 的参与者直接安装，写入宿主配置、hooks 或目标项目生产源码的参与者按各自参考取得授权。安装后汇报 scope、写入路径与结果，并重新验证。若宿主需要重载才能发现新 Skill，报告重载方式并停止依赖它的阶段。

## 通用流程

### 1. 建立共同输入

定位目标项目和任务边界，收集产品事实、现有行为、设计证据、技术约束和验证要求。为每个参与者声明本次职责、输入、预期输出及不可改变的约束。

### 2. 建立执行基线

先运行拥有项目基础层或设计系统权威的参与者。它返回可执行契约、现有能力、页面资源建议、实施边界和已知缺口。当前采用 Untitled UI 时，该阶段由 `untitled-ui` 完成。

后续参与者必须把执行基线视为 pinned brief 与 incumbent truth；在基线返回前，不生成与之平行的技术或视觉方向。

### 3. 专项设计与审查

按参与者登记的职责，把共同输入、完整基线和 `untitled-ui` 提供的资源建议交给对应专家或调用 Agent。页面设计方使用这些资源决定产品流程、信息架构、内容层级、布局、响应式和页面组合，不自行搜索、选择或安装基础层资源；现有资源无法满足方案时，只返回能力需求，不直接修改基础层或实现规则。

当前流程中，`impeccable` 在此阶段负责产品体验设计、资源组合或审查；`animate` 在此阶段负责动效方案与实现。

### 4. 归口实施

把专项方案交回拥有实现权威的参与者，由它确认契约适配性、选择资源、处理缺口并实施。当前采用 Untitled UI 时，最终界面实现与技术验证归 `untitled-ui`。

### 5. 分层验收

各参与者先验证自己负责的结果，再由编排层聚合：

- 实现方确认构建、组件、主题、交互、可访问性和兼容性。
- 专项参与者确认产品流程、信息层级、响应式和体验质量。
- 编排层确认交接完整、冲突已归口、授权边界未被扩大。

集中完成一次修复回流和一次最终复核；各 Skill 自己规定的更严格验证仍然适用。

## 冲突与回流

1. 用户明确要求、产品事实和必须保留的行为优先。
2. 基础层拥有者决定其设计系统、组件和实现边界。
3. 专项参与者在该边界内决定自己负责的方案。
4. 超出边界的建议先回到边界拥有者确认可行方案或最小缺口，不直接实施。
5. 仍需扩展、替换或迁移时，向用户说明影响并取得明确授权。

品牌色、设计系统 token 与基础组件属于第 1、2 条覆盖的范围：已由用户提示词或项目默认值确定的品牌色不再作为设计议题，专项设计参与者不得替换、调整或另行生成配色。设计方认为基础层选择不适配时，只提出建议并交回边界拥有者或用户确认。

问题按所有权回流，不让多个 Skill 同时修改同一问题：产品与体验问题回到对应设计参与者；资源、实现和兼容问题回到基础层或实现参与者；安装、hooks、生成文件和 Git 管理问题按特殊事项参考处理。

动效与动画归 `animate`：动效请求由它承担设计与实现，其他参与者不代为承担，也不以自身的动效能力接管这类请求。需要新增或修改设计系统 token、或需要改动组件源码的动效需求，按第 2、4 条交回基础层拥有者或用户确认。

## 交付

最终汇报只聚合：

- 实际参与的 Skills 及各自职责。
- 共同输入、执行基线和关键交接结果。
- 各参与者的设计、实施与验证结论。
- 冲突回流、能力缺口、特殊集成处理和明确授权。
- 剩余限制及其负责方。
